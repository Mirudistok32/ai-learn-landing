    01

    Общая картина

    Почти вся путаница в AI — от смешения уровней. Сначала форма: человек говорит с приложением; приложение вызывает модель; если нужны действия и несколько шагов — появляется агент (цикл + tools); внешние системы делают реальную работу.

    На человеческом языке: модель — это «мозг, который пишет текст». Агент — это «мозг + руки + цикл попыток», пока задача не решена. ChatGPT — приложение. GPT — модель внутри него. Cursor — тоже приложение, которое оркестрирует модели за вас.

    ПРИМЕР

    «Найди баг в auth и почини» → агент читает файлы, запускает тесты, правит код, снова проверяет — пока не закончит.

    02

    Models — модели

    Model — это обученная нейросеть: на вход текст (и иногда картинки), на выход — продолжение. Всё остальное в стеке — providers, API, agents, IDE — обвязка вокруг этого «мозга».

    На человеческом языке: модель не «понимает» мир как человек. Она предсказывает следующий кусок текста (token) так, чтобы ответ выглядел правдоподобно. Отсюда сила — и галлюцинации.
    INPUT
    MODEL
    OUTPUT

    Модель ≠ агент (запомните это)

    MODEL

    Только генерация. Спросила — ответила. Не открывает файлы, не ходит в интернет сама, не «решает задачу до конца» без вашей обвязки.

    АНАЛОГИЯ

    Калькулятор: вы нажали кнопки — он посчитал один раз.

    AGENT

    Модель + инструкции + tools + цикл. Может читать репозиторий, вызывать API, проверять результат и пробовать снова.

    АНАЛОГИЯ

    Стажёр с доступом к ноутбуку: думает, кликает, проверяет, пока задача не закрыта.

    Пять уровней — не путайте

    MODEL

    Сам AI. GPT‑5.x, Claude Opus/Sonnet, Gemini, DeepSeek, Qwen — это модели (семейства).

    PROVIDER

    Компания, которая обучает и отдаёт модели через API: OpenAI, Anthropic, Google, DeepSeek, Alibaba…

    APPLICATION

    Ваш код или продукт (ChatGPT, Cursor, ваш SaaS). Вызывает API, даёт tools, хранит memory.

    API

    HTTPS-интерфейс: приложение шлёт сообщения, получает tokens ответа (часто streaming).

    AGENT

    Паттерн поверх модели: instructions + tools + execution loop — не отдельный «вид модели».

    Как обучают модели (кратко)

    Обучение — это не «загрузить PDF». Это огромный вычислительный процесс у провайдера. Вы платите уже за inference — запуск готовой модели.

    1 · PRETRAINING

    Модель читает терабайты текста/кода из интернета и книг и учится предсказывать следующий token. Получается «общий язык», но ещё не удобный ассистент.

    2 · SFT / INSTRUCTION

    Дообучение на примерах «вопрос → хороший ответ». Модель учится следовать инструкциям, а не просто продолжать текст.

    3 · ALIGNMENT (RLHF / RLAIF)

    Люди или AI-судьи оценивают ответы; модель подтягивают к полезным, безопасным, честным ответам. Отсюда «тон» ChatGPT и Claude.

    Дальше возможны специализации: reasoning-модели (дольше «думают»), coding-модели, multimodal (текст+картинки+видео), open-weight (веса можно скачать и self-host).

    03

    API

    Вы никогда не запускаете модель сами. Приложение отправляет HTTPS-запросы к provider API, и результат модели приходит в ответе — обычно в режиме streaming, токен за токеном.

    YOUR APPLICATION
    PROVIDER API
    MODEL
    RESPONSE

    API KEY

    Секретный credential, привязанный к аккаунту и биллингу. Аутентифицирует каждый запрос.

    REQUEST

    Сообщения + параметры: model, instructions, context, tool definitions.

    RESPONSE

    Сгенерированный выход + usage: сколько tokens потрачено.

    STREAMING

    Токены приходят по мере генерации — не нужно ждать весь ответ целиком.

    ERRORS

    Ответы 4xx / 5xx. Обрабатывайте их: повторы, backoff, понятные фолбэки.

    RATE LIMITS

    Запросы и tokens в минуту. Превысите — и API начнёт отказывать.

    Minimal call (provider-agnostic)

    TYPESCRIPT 
    // Вызов API провайдера с сервера — никогда из браузера
const res = await fetch("https://api.provider.com/v1/messages", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": "Bearer " + process.env.PROVIDER_API_KEY,
  },
  body: JSON.stringify({
    model: "some-model-name",

  }),

const data = await res.json();
console.log(data.output);

    Context Window

    Context window — это всё, что модель видит в рамках одного запроса: инструкции, история, документы, tool definitions, результаты инструментов, текущая просьба. Не «память» — видимость в пределах одного запроса.

    CONTEXT WINDOW — ONE REQUEST
    System instructions
    User messages
    Previous conversation
    Documents
    Tool definitions
    Tool results
    Current request
    Всё должно поместиться. Когда окно заполняется, старое содержимое усекается или отбрасывается. Пропорции иллюстративные.
    DON'T CONFUSE
    Context≠Memory — контекст живёт внутри одного запроса; memory — то, что приложение сохраняет между ними.

    DEEPER DIVE

    Prompt и Prompt Engineering

    Prompt — это весь вход, который модель видит за один запрос: системные инструкции + контекст + ваше сообщение (+ примеры). Prompt engineering — умение собрать этот вход так, чтобы ответ был полезным, стабильным и безопасным.

    На человеческом языке: модель не «читает мысли». Она отвечает на то, что буквально лежит во входе. Плохой промпт ≈ размытая задача коллеге без контекста. Хороший — роль, цель, ограничения, формат, пример.

    +
    CONTEXT
    +
    USER REQUEST
    =
    MODEL INPUT

    SYSTEM / DEVELOPER

    Постоянные правила: роль, тон, запреты, формат ответа. Применяются к каждому запросу.

    CONTEXT

    Документы, куски кода, результаты tools — то, чего модель не знала из обучения.

    USER INPUT

    Конкретная просьба человека прямо сейчас.

    EXAMPLES (few-shot)

    1–3 образца «вход → желаемый выход». Часто сильнее длинных словесных правил.

    Мини-паттерны prompt engineering

    ROLE + GOAL + CONSTRAINTS

    «Ты X. Цель — Y. Не делай Z. Формат — JSON/таблица/код.» Три опоры почти любого рабочего промпта.

    SHOW, DON'T ONLY TELL

    Добавьте пример желаемого ответа. Модели лучше копируют паттерн, чем абстрактные правила.

    SEPARATE DATA FROM INSTRUCTIONS

    Документы и user input — в отдельных блоках/тегах. Так меньше шансов, что модель перепутает «инструкцию» с «данными».

    ITERATE + EVAL

    Один «идеальный» промпт редко рождается с первого раза. Меняйте по одному рычагу и проверяйте на фиксированных примерах (evals).

    TYPESCRIPT · СБОРКА ПРОМПТА 
    function buildPrompt(userAsk: string, docs: string[]) {
  return [
    { role: "system", content: "Ты помощник поддержки. Отвечай только по документам. Если ответа нет — скажи об этом." },
    { role: "user", content:
      `Документы:\n${docs.join("\n---\n")}\n\nВопрос:\n${userAsk}`
    },
  ];
}
    ГЛАВНОЕ

    Prompt engineering — не магия и не «секретные слова». Это ясная постановка задачи + нужный контекст + проверяемый формат ответа. В агентах ту же роль играют rules, skills и hooks.

    DEEPER DIVE

    Structured Output

    Свободный текст — для людей. Приложениям нужна структура, которую можно парсить и валидировать, — поэтому выход модели ограничивают schema.

    PLAIN TEXT 
    Ответ — Париж.
    JSON · STRUCTURED 
    {
  "city": "Париж",
  "country": "Франция"
}
    WHY

    Со structured output ваш код может надёжно парсить ответ, валидировать его по схеме и передавать следующему шагу — вместо регэкспов по абзацу прозы.

    Tools

    Tool — это возможность, которую приложение даёт модели: читать файлы, искать в вебе, ходить в базу, вызывать API. Модель не может действовать на мир — tools это то, как она просит ваш код действовать.

    KEY IDEA

    Модель может сгенерировать tool call. Приложение исполняет tool. Модель ничего не запускает сама — она только предлагает.

    07

    Tool Calling

    Проследите за одним запросом сквозь цикл: модель предлагает структурированный tool call, приложение исполняет его, результат возвращается к модели — и она завершает ответ.

    INTERACTIVE DEMO · TOOL CALLINGREADY

    Что только что произошло, по порядку:

    • Модель получила запрос плюс tool definition (имя, описание, параметры).
    • Она поняла, что нужны данные — и сгенерировала tool call: JSON с именем и аргументами.
    • Ваше приложение распарсило его, вызвало настоящий API и дописало результат в диалог.
    • Модель увидела результат и выдала финальный ответ.

    08

    Agents — агенты

    Агента делает агентом не «умная модель», а цикл: модель думает → предлагает tool → приложение исполняет → результат возвращается → пока цель не достигнута.

    Модель vs агент ещё раз: спросили Claude в чате «что такое JWT?» — это модель. Попросили Cursor «найди утечку памяти и почини» — это агент: он сам открывает файлы, запускает команды, правит код в цикле.

    The agent loop

    NO → цикл делает ещё один круг · YES → agent возвращает финальный ответ. Конкретные архитектуры различаются (ReAct, planner–executor и др.) — цикл у них общий.

    MCP — Model Context Protocol

    Раньше каждая интеграция была кастомным клеем. MCP — открытый протокол, стандартизирующий то, как AI-приложения обнаруживают и используют внешние tools и источники данных.

    DEFINITION

    MCP — Model Context Protocol: открытый стандарт подключения AI-приложений к внешним tools и источникам данных единообразным, обнаруживаемым способом.

    MCP is not:a modelan agentan API provideran AI IDE

    RESOURCES

    MCP CLIENT

    Живёт внутри AI-приложения. Говорит на протоколе, обнаруживает, что предлагают серверы.

    MCP SERVER

    Программа, экспортирующая возможности — обычно обёртка над одной внешней системой.

    EXTERNAL SYSTEM

    То, что реально хранит данные или делает работу.

    MCP vs API

    API MCP
    способ взаимодействия с конкретным сервисом протокол, стандартизирующий AI ↔ tools/data

    Memory

    Rules, Skills, Commands, Subagents, Hooks

    Пять механизмов, которые превращают coding-агента из «умного чата» в предсказуемого напарника. Ниже — живые примеры в духе agent-base: rules, skill, command, hooks.json.

    Rules

    Rule — постоянная инструкция для агента в этом проекте: стандарты, запреты, «как мы здесь пишем код». Подхватывается автоматически, вы её каждый раз не вставляете в чат.

    Когда нужен rule: «всегда TypeScript strict», «не трогай биллинг без ревью», «domain — pure, без React». Когда не нужен: одноразовая задача «переименуй кнопку» — это обычный чат.
    .cursor/rules/architecture.mdc 
    ---
description: Shared clean architecture — inward deps, pure domain
alwaysApply: true
---

# Architecture
Dependencies point inward only:
app / routes → presentation → application → domain ← infrastructure

- domain — pure. No React, router, window, storage.
- No classes as default — functions, plain objects, unions.
- Immutability — domain ops return new objects.

    Skills

    Skill — переиспользуемый сценарий: когда применять + шаги + чек-листы. Агент сам подхватывает skill, если задача совпала с description — или вы зовёте его явно.

    skills/adapt-responsive-ui/SKILL.md 
    ---
name: adapt-responsive-ui
description: >-
  Audit UI for phones/tablets. Use when changing layout, CSS, nav, forms,
  or when the user mentions mobile / viewport / adaptive UI.
---

# Adapt responsive UI
1. Read adaptive-ui docs + project design tokens
2. Fix with CSS first: fluid widths, min-w-0, safe-area, dvh
3. Touch targets ≥ 44px
4. Verify ~320px, phone, tablet, one landscape
    СТРУКТУРА SKILL 
    cursor/skills/adapt-responsive-ui/
├── SKILL.md          # когда и как применять
└── (опционально)
    ├── references/   # чек-листы
    └── scripts/      # вспомогательные скрипты

    Commands

    Command — кнопка, которую запускаете вы: именованный workflow в чате (например /check). В отличие от skill, агент сам его обычно не выбирает.

    .cursor/commands/check.md 
    Run the project’s quality gate and fix failures.

1. Detect scripts from package.json (check, lint, typecheck, test, build).
   Prefer npm run check when defined.
2. If missing, compose: typecheck + lint + format check.
3. Fix errors in the files you own; re-run until green.

Do not invent Next-only or Vite-only steps the repo doesn’t use.

    Command = явный триггер («сделай именно это»). Skill = знание, которое агент может применить сам, когда уместно.

    Subagents

    Subagent — отдельный исполнитель со своим context window, которому главный агент делегирует кусок работы — чтобы не засорять основной контекст.

    ← DRAG TO EXPLORE
    NOTE

    Subagents не нужны для каждой задачи — делегирование окупается на изолированной, параллелизуемой или тяжёлой для контекста работе.

    Hooks

    Hook — реакция на событие жизненного цикла агента: автоматическая и детерминированная. Модель её не «решает» — сработало событие → выполнился скрипт.

    Пример из практики: после каждого редактирования файла автоматически прогнать formatter. Агент пишет код — hook наводит порядок, без отдельной просьбы «отформатируй».
    .cursor/hooks.json 
    {
  "version": 1,
  "hooks": {
    "afterFileEdit": [
      { "command": ".cursor/hooks/format.mjs" }
    ]
  }
}

    BEFORE TOOL
    guard · validate
    TOOL
    executes
    AFTER TOOL
    format · audit
    format codesecurity checkvalidate shell command audit changesinject context
