    01

    Общая картина

    Почти любая путаница в AI возникает из смешения уровней стека. Прежде чем разбираться в деталях — посмотрите на форму: пользователь общается с приложением; приложение вызывает модель; агент добавляет инструменты и цикл; внешние системы делают реальную работу.

    02

    Модели

    Модель — это сам AI: она получает вход и генерирует выход. Всё остальное в стеке — провайдеры, API, агенты, IDE — это бизнес-логика, протоколы и обвязка вокруг неё.

    ВХОД
    МОДЕЛЬ
    ВЫХОД

    Пять вещей, которые нужно различать

    МОДЕЛЬ

    AI, который генерирует выход из входа. GPT, Claude и Gemini — модели.

    ПРОВАЙДЕР

    Компания, которая обучает и обслуживает модели через API — OpenAI, Anthropic, Google.

    ПРИЛОЖЕНИЕ

    Ваш код. Он вызывает API, предоставляет инструменты, хранит память, запускает агентов.

    API

    HTTPS-интерфейс между вашим приложением и моделями провайдера.

    АГЕНТ

    Паттерн поверх модели: инструкции + инструменты + цикл исполнения.

    03

    API

    Вы никогда не запускаете модель сами. Приложение отправляет HTTPS-запросы к API провайдера, и выход модели возвращается в ответе — обычно потоково, токен за токеном.

    ВАШЕ ПРИЛОЖЕНИЕ
    API ПРОВАЙДЕРА
    МОДЕЛЬ
    ОТВЕТ

    API-КЛЮЧ

    Секретный credential, привязанный к аккаунту и биллингу. Аутентифицирует каждый запрос.

    ЗАПРОС

    Сообщения + параметры: модель, инструкции, контекст, определения инструментов.

    ОТВЕТ

    Сгенерированный выход + usage: сколько токенов потрачено.

    СТРИМИНГ

    Токены приходят по мере генерации — не нужно ждать весь ответ целиком.

    ОШИБКИ

    Ответы 4xx / 5xx. Обрабатывайте их: повторы, backoff, понятные фолбэки для пользователя.

    RATE LIMITS

    Запросы и токены в минуту. Превысите — и API начнёт отказывать.

    Минимальный вызов (провайдер-агностично)

    TYPESCRIPT 
    // Вызов API провайдера с сервера — никогда из браузера
const res = await fetch("https://api.provider.com/v1/messages", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    "Authorization": "Bearer " + process.env.PROVIDER_API_KEY,
  },
  body: JSON.stringify({
    model: "some-model-name",
    messages: [{ role: "user", content: "Привет!" }],
  }),
});

const data = await res.json();
console.log(data.output);

    04

    Токены

    Токен — фрагмент текста: часто слово, часть слова или пунктуация. Не обязательно слово. Это единица, которой модель читает, пишет — и за которую вы платите.

    "Привет, мир"
    Привет
    мир
    ИНТЕРАКТИВ · МАК-ТОКЕНИЗАТОРПОПРОБУЙТЕ

    Упрощённый мак — реальные токенизаторы (BPE и родня) режут иначе, но идея та же: текст → фрагменты → числа. Выход здесь — токенизация заготовленного ответа.

    БОЛЬШЕ КОНТЕКСТА
    БОЛЬШЕ ТОКЕНОВ
    ВОЗМОЖНО ВЫШЕ ЦЕНА
    ГЛАВНОЕ

    Оплачиваются и входные (то, что вы отправили), и выходные (то, что сгенерировала модель) токены — и всё, что напихано в контекст, считается входом.

    05

    Окно контекста

    Окно контекста — всё, что модель видит в одном запросе: инструкции, история, документы, определения инструментов, их результаты, текущая просьба. Не «память» — видимость в пределах одного запроса.

    ОКНО КОНТЕКСТА — ОДИН ЗАПРОС
    Системные инструкции
    Сообщения пользователя
    Предыдущий диалог
    Документы
    Определения инструментов
    Результаты инструментов
    Текущий запрос
    Всё должно поместиться. Когда окно заполняется, старое содержимое усекается или отбрасывается. Пропорции иллюстративные.
    НЕ ПУТАТЬ
    Context≠Memory — контекст живёт внутри одного запроса; память — то, что приложение сохраняет между ними.
    СВЯЗАННЫЕ ПОНЯТИЯ
    → Промпт→ Память→ RAG

    Промпт

    СИСТЕМНЫЕ / РАЗРАБОТЧИКА

    Постоянные инструкции: роль, формат, ограничения. Применяются к каждому запросу.

    КОНТЕКСТНЫЕ

    Документы, найденные фрагменты, результаты инструментов — то, чего модель не знала.

    ВВОД ПОЛЬЗОВАТЕЛЯ

    Конкретная просьба человека прямо сейчас.

    ПРИМЕРЫ

    Few-shot образцы, показывающие нужный паттерн. Опционально, но мощно.

    Эта карта сознательно не углубляется в промпт-инжиниринг — отдельное ремесло на том же фундаменте.

    ДОПОЛНИТЕЛЬНО

    Структурированный вывод

    Свободный текст — для людей. Приложениям нужна структура, которую можно парсить и валидировать — поэтому выход модели ограничивают схемой.

    ПРОСТОЙ ТЕКСТ 
    Ответ — Париж.
    JSON · СТРУКТУРА 
    {
  "city": "Париж",
  "country": "Франция"
}
    ЗАЧЕМ

    Со структурированным выводом ваш код может надёжно парсить ответ, валидировать его по схеме и передавать следующему шагу — вместо регэкспов по абзацу прозы.

    06

    Инструменты

    Инструмент — это возможность, которую приложение даёт модели: читать файлы, искать в вебе, ходить в базу, вызывать API. Модель не может действовать на мир — инструменты это то, как она просит ваш код действовать.

    КЛЮЧЕВАЯ ИДЕЯ

    Модель может сгенерировать вызов инструмента. Приложение исполняет инструмент. Модель ничего не запускает сама — она только предлагает.

    МОДЕЛЬ

    07

    Tool Calling

    Проследите за одним запросом сквозь цикл: модель предлагает структурированный вызов, приложение исполняет его, результат возвращается к модели, и она завершает ответ.

    ИНТЕРАКТИВНАЯ ДЕМО · TOOL CALLINGГОТОВ

    Что только что произошло, по порядку:

    • Модель получила запрос плюс определение инструмента (имя, описание, параметры).
    • Она поняла, что нужны данные — и сгенерировала вызов инструмента: JSON с именем и аргументами.
    • Ваше приложение распарсило его, вызвало настоящий API и дописало результат в диалог.
    • Модель увидела результат и выдала финальный ответ.

    → Инструменты→ Агенты→ MCP
    08

    Агенты

    Что превращает агента в агента? Не модель — цикл. Агент — это модель с инструкциями и инструментами, работающая в цикле исполнения до достижения цели.

    МОДЕЛЬ
    +
    ИНСТРУКЦИИ
    +
    ИНСТРУМЕНТЫ
    +
    ЦИКЛ ИСПОЛНЕНИЯ
    =
    АГЕНТ

    Цикл агента

    НЕТ → цикл делает ещё один круг · ДА → агент возвращает финальный ответ. Конкретные архитектуры различаются (ReAct, planner–executor и др.) — цикл у них общий.

    ИНТЕРАКТИВНАЯ ДЕМО · СИМУЛЯЦИЯ АГЕНТАГОТОВ

    Симуляция на локальных данных — без реальной модели и API-вызовов. Суть — в концепции.

    Чат-бот vs Агент

    Чат-бот Агент
    отвечает выполняет
    обычно один ответ несколько шагов
    ограничен текущим вводом использует инструменты
    не обязательно действует может совершать действия
    модель модель + исполнение

    Граница не абсолютна — это архитектурная классификация, а не догма.

    09

    MCP — Model Context Protocol

    Раньше каждая интеграция была кастомным клеем. MCP — открытый протокол, стандартизирующий то, как AI-приложения обнаруживают и используют внешние инструменты и источники данных.

    ОПРЕДЕЛЕНИЕ

    MCP — Model Context Protocol: открытый стандарт подключения AI-приложений к внешним инструментам и источникам данных единообразным, обнаруживаемым способом.

    MCP — это НЕ:не модельне агентне API-провайдерне AI IDE

    Архитектура MCP

    AI-ПРИЛОЖЕНИЕ
    MCP-КЛИЕНТ
    MCP-СЕРВЕР
    TOOLS
    исполняемые действия
    RESOURCES
    данные, которые можно читать
    PROMPTS
    переиспользуемые шаблоны

    MCP-КЛИЕНТ

    Живёт внутри AI-приложения. Говорит на протоколе, обнаруживает, что предлагают серверы.

    MCP-СЕРВЕР

    Программа, экспортирующая возможности — обычно обёртка над одной внешней системой.

    ВНЕШНЯЯ СИСТЕМА

    То, что реально хранит данные или делает работу.

    Демо архитектуры — не настоящий MCP-сервер. Снапшот спеки: … · MCP развивается, см. modelcontextprotocol.io.

    MCP vs API

    API MCP
    способ взаимодействия с конкретным сервисом протокол, стандартизирующий AI ↔ инструменты/данные
    проектируется каждым провайдером спроектирован для AI-приложений
    конкретные endpoint стандартизированное объявление возможностей
    REST / GraphQL / и т.д. MCP

    MCP не «заменяет все API» — это слой интеграции между вашим AI-приложением и существующими системами, у которых по-прежнему есть API.

    RAG — Retrieval-Augmented Generation

    Модели знают свои обучающие данные — но не ваши. RAG находит релевантные документы и кладёт их в контекст модели, поэтому ответы опираются на ваши знания, а не придумываются.

    ДОКУМЕНТЫ
    ЧАНКИНГ
    ЭМБЕДДИНГИ
    ВЕКТОРНАЯ БД
    ПОИСК
    РЕЛЕВАНТНЫЙ КОНТЕКСТ
    LLM
    ОТВЕТ
    ИНТЕРАКТИВ · СИМУЛЯЦИЯ RAGГОТОВ

    БАЗА ЗНАНИЙ

    Визуальная симуляция — без настоящего эмбеддинг-пайплайна. Попробуйте также «оплата» или «отпуск».

    Эмбеддинги

    Эмбеддинг — числовое представление смысла: похожие тексты оказываются рядом в векторном пространстве, что делает возможным поиск по схожести.

    "Как сбросить пароль"→[0.12, -0.42, 0.07, …]РЯДОМ
    "Забыл пароль"→[0.14, -0.39, 0.05, …]РЯДОМ
    "Погода в Вене"→[-0.31, 0.22, 0.58, …]ДАЛЕКО

    Векторные базы

    ДОКУМЕНТЫ
    ЭМБЕДДИНГИ
    ВЕКТОРНАЯ БД
    ПОИСК ПО СХОЖЕСТИ
    PineconeQdrantWeaviatepgvector

    Названия — только ориентир, это не обзор продуктов.

    RAG vs MCP

    RAG MCP
    поиск и предоставление релевантного контекста подключение инструментов и данных
    обычно для знаний обычно для интеграций
    эмбеддинги — центральное эмбеддинги не обязательны
    пайплайн поиска протокол
    ГЛАВНОЕ

    RAG и MCP решают разные задачи и могут использоваться одновременно: MCP подключает ваши системы, RAG заземляет ответы в их содержимом.

    11

    Память

    Четыре похожих по звучанию и разных по сути вещи. Различение их решает половину споров об «AI-архитектуре».

    Понятие Что это Жизненный цикл Пример Не путать с
    Контекст что модель видит сейчас один запрос сообщения + документы в промпте с памятью
    Память что приложение помнит между взаимодействиями между сессиями «этот пользователь предпочитает TypeScript» с контекстом
    База данных где живут структурированные данные приложения постоянно таблица users с RAG
    RAG как внешние знания попадают в контекст при каждом поиске документы → эмбеддинги → векторная БД → промпт с базой данных
    ГЛАВНОЕ

    У модели нет памяти. Память есть у вашего приложения — и оно решает, какой её кусок влезает в окно контекста каждого запроса.

    Rules, Skills, Commands, Subagents, Hooks

    Пять механизмов, превращающих кодинг-агентов из хаотичных в надёжных. Каждый отвечает на свой вопрос — таблица в конце это шпаргалка.

    Rules

    Rule — постоянная инструкция, направляющая агента в каждой задаче: стандарты кодинга, конвенции, запреты.

    .cursor/rules/project.mdc 
    ---
description: Конвенции проекта
---
- Всегда используй TypeScript в strict-режиме
- Для стилей — CSS Modules
- Никогда не используй setTimeout для синхронизации скролла — только IntersectionObserver

    Skills

    Skill — специализированный переиспользуемый сценарий, который агент применяет, когда тот уместен: знания + шаги + справочники, упакованные вместе.

    СТРУКТУРА SKILL 
    skills/frontend-review/
├── SKILL.md        # когда и как применять
├── references/     # чек-листы, гайды по стилю
└── scripts/        # опциональные вспомогательные скрипты

    Commands

    Command — заранее определённый сценарий, который вы запускаете явно: именованная кнопка для повторяемого действия.

    КОМАНДЫ 
    /review             → полное код-ревью
/test               → сгенерировать и запустить тесты
/create-component   → создать новый компонент

    Commands и skills пересекаются, но не совпадают: command — явный триггер; skill — возможность, которую агент может задействовать сам, когда она уместна.

    Subagents

    Subagent — отдельный специализированный исполнитель со своим окном контекста, которому главный агент делегирует работу — сохраняя главный контекст чистым.

    ← ПОТЯНИТЕ, ЧТОБЫ ОСМОТРЕТЬ
    ВАЖНО

    Сабагенты не нужны для каждой задачи — делегирование окупается на изолированной, параллелизуемой или тяжёлой для контекста работе.

    Hooks

    Hook — реакция на событие жизненного цикла агента: автоматическая, детерминированная, не решается моделью.
